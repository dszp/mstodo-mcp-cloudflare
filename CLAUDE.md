# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

A single-user, single-tenant **MCP server for Microsoft To Do**. It exposes ~50 MCP tools (list/task CRUD, checklist items, linked resources, attachments, My Day, search, config) backed by a SQLite cache with Graph delta sync. Host-independent code lives in `packages/core`; it runs on two hosts: the primary **Cloudflare Worker** (`workers/server/src/hosts/cloudflare`, SQLite in a Durable Object) and a **Node.js / Docker** host for self-hosting elsewhere (`workers/server/src/hosts/node`, one SQLite file). `workers/server/src/hosts/shared` holds the OAuth front both hosts use.

The server is becoming the backend of **Potem**, a task app for macOS and iOS that replaces the Microsoft To Do apps. The apps live in a separate repository and talk to this server only through the client sync API under `/api/v1`; `docs/SYNC-API.md` is that contract. The project was `mstodo-mcp` until 0.18.0, and the repository `dszp/mstodo-mcp-cloudflare` until it was renamed `dszp/potem-server`; existing deployments keep their Worker names, and code identifiers such as `MSToDoSession`, the `service` field in `/health` and the Node host's `MSTODO_DB` keep the old name, because renaming them breaks deployed state. ROADMAP.md sections 12 to 15 record where the project is headed: the repository layout, adapter workers, Microsoft To Do as an optional backend, and deploying to several Cloudflare accounts.

## Commands

```bash
pnpm run dev <name>      # wrangler dev for deployments/<name>, using its .dev.vars
pnpm test             # vitest run (all tests, via @cloudflare/vitest-pool-workers)
pnpm run test:watch   # vitest watch mode
pnpm run types        # wrangler types from workers/server/wrangler.example.jsonc into workers/server/worker-configuration.d.ts; rerun after binding changes
pnpm run render|check|dry-run|deploy|secrets|tail <name> [flags]      # named deployments, see below
pnpm run build:node   # esbuild the Node host into dist/main.mjs
pnpm run start:node   # node dist/main.mjs (needs SERVICE_BASE_URL + the MS_* / OWNER_EMAIL env)
pnpm run web:dev      # Vite dev server for the web app (workers/web); answers /bff and /auth from a fake BFF (src/app/dev/fake-bff.ts), no server needed
pnpm run web:build    # build the web app into workers/web/dist (wrangler runs this on deploy)
pnpm run web:spike    # Vite dev server for the web spike (workers/web/spike), synthetic feed
pnpm run web:spike:prod   # production build of the spike, then vite preview

pnpm exec vitest run workers/server/test/move-task.test.ts   # one test file
pnpm exec vitest run -t "reparent"                    # tests matching a name
pnpm exec vitest run --project workers                # Cloudflare pool only (workers/server/test/**)
pnpm exec vitest run --project node                   # Node host and deployment tools (workers/server/test-node/**, scripts/deployment/test/**)
pnpm exec vitest run --project web                    # web client (workers/web/**)
pnpm exec tsc --noEmit -p .                           # typecheck (Workers types)
pnpm exec tsc -p tsconfig.node.json                   # typecheck core + Node host with Node-only types
pnpm exec tsc --noEmit -p workers/web                 # typecheck the web app and spike (DOM, JSX)
pnpm exec tsc --noEmit -p workers/web/tsconfig.worker.json   # typecheck the BFF and the Cloudflare host (Workers types, no DOM)
pnpm exec tsc --noEmit -p workers/web/tsconfig.engine.json   # typecheck the sync engine: ES2022 only, no DOM/Node/Workers globals
```

**Tests need no real credentials or live config.** `vitest.config.ts` defines three projects; `web` (`workers/web/**`) runs the web client's tests. `workers` (`workers/server/test/**`) points the Cloudflare pool at the committed `workers/server/wrangler.example.jsonc` and supplies fake secrets via miniflare bindings; KV and DO bindings are simulated locally. `workers/server/test/_test-worker.ts` re-exports only `TodoIndex` (the `MSToDoSession` agent DO is deliberately excluded — it pulls in the MCP SDK → ajv, which the pool can't resolve). `node` (`workers/server/test-node/**` and `scripts/deployment/test/**`) runs on plain Node 24 with in-memory `node:sqlite` databases and fake `MS_*` values passed to `buildNodeEnv`; Microsoft endpoints are stubbed with `vi.stubGlobal("fetch")`. Node ≥ 24.2 is required for development (`node:sqlite`, and `import.meta.main` in `scripts/deployment/cli.ts`).

## Deployments

Each deployment is a folder, `deployments/<name>/` (gitignored), holding `deployment.jsonc` (account ID, Worker name, `base_url`, custom domains, KV IDs, R2 buckets, var overrides; shape in the committed `deployment.example.jsonc`), `.dev.vars` and `last-deployed.json`. The scripts in `scripts/deployment/` render `workers/server/wrangler.example.jsonc` plus that file, run the checks, write the result to `.wrangler/deployments/<name>/rendered.json` and run wrangler against it with `-c`. A deployment that fails a check has no `rendered.json`; run `pnpm run check <name>` before pointing a direct wrangler command at it. There is no root `wrangler.jsonc`, so a bare `wrangler deploy` has no config to pick. The committed `workers/server/wrangler.example.jsonc` is the one place bindings, migrations and default vars live, and CI and the tests use it.

- **Commands** all take the name: `render` prints the config; `check` validates locally and reads the live Worker; `dry-run` builds without uploading; `deploy` confirms the changes since `last-deployed.json`; `secrets` pushes `.dev.vars` to the Worker (`op://` references resolved by `op`, values over stdin); `dev` and `tail` run wrangler against the rendered config. Wrangler flags pass through only when `scripts/deployment/args.ts` lists them for that command.
- **New deployment order:** create the KV namespaces and the R2 bucket, write `deployment.jsonc` and `.dev.vars`, `pnpm run check`, `pnpm run deploy` (first deploy, interactive confirm), then `pnpm run secrets`, which refuses until the Worker exists, then authorize.
- **`deploy` needs an interactive terminal** (stdin and stdout on a TTY, `CI` unset). `--non-interactive` skips the prompt and refuses any pending config change. `--adopt` is only for taking over an existing Worker whose KV bindings don't match the file.
- **Account:** wrangler takes the account from the rendered config's `account_id`. The script also sets `CLOUDFLARE_ACCOUNT_ID` for its children and refuses to run if the shell already has a different one, or sets `CLOUDFLARE_ENV` or `WRANGLER_CI_OVERRIDE_NAME` (each redirects wrangler to another Worker). Children get `--env=` and the Worker name pinned, so a root `.env` can't supply either.
- **Production serves the owner's real To Do account.** Don't create or edit test data there. Test against a secondary deployment, and give test lists and tasks a recognizable prefix so they can be found and deleted.
- **Changing the hostname creates new grants.** Tokens are bound to `<origin>/mcp` and `<origin>/api/v1`, and `buildOAuthFront(origin)` builds the front per request, so a second hostname on the same Worker works alongside the first, but every client must sign in again on the new one. Before moving, add `https://<new host>/auth/microsoft/callback` to the Entra app's redirect URIs. Then update `SERVICE_BASE_URL`: it sets the Graph subscription `notificationUrl` and the upload and download link origin. Retire the old hostname only after the connectors and the apps have moved.

## Upgrading wrangler

Treat a wrangler upgrade as a code change, in its own PR, never as a routine dependency bump. `scripts/deployment/` relies on wrangler behaviour that its tests stub out, so a green suite doesn't prove the new version still behaves that way. `package.json` pins wrangler to an exact version so that `pnpm install` and Dependabot can't move it silently; handle a Dependabot PR for wrangler with this procedure, not by merging it.

Each relied-on behaviour is cited in a code comment by its line in `node_modules/wrangler/wrangler-dist/cli.js` (search the scripts and tests for `cli.js`). The ones that matter:

| Behaviour | Relied on in | If it changes |
|---|---|---|
| `--env=` (empty) selects no environment and adds no name suffix; `CLOUDFLARE_ENV` and `WRANGLER_CI_OVERRIDE_NAME` redirect the Worker; `.env` loads through dotenv-expand, where a truthy process value wins | `checks.ts` | A deploy can silently reach another Worker |
| The argument parser reads `--flag=value` as one value and treats a separate token starting with `-` as a flag | `args.ts` | A passed-through value can become a flag |
| `deploy --strict` exists and aborts on non-interactive config prompts | `cli.ts` | Config prompts auto-accept off a TTY |
| `secret put` on a missing Worker creates a draft Worker | `cli.ts` (`secrets` refuses first) | Harmless: `secrets` refuses before wrangler runs |
| `auth token --json` output shape and token types | `live.ts` `wranglerToken` | Refuses: "could not read the token" |
| The Cloudflare API calls and shapes wrangler's SDK uses (script settings, domains list, domain changeset, subdomain; error code 10007 for a missing Worker) | `live.ts` | Refuses: "could not verify the live Worker" |
| Custom domains are replaced (`replace_state=true`) only when the config has custom-domain routes | `cli.ts` `detachedDomains` | A detach goes unannounced |
| `.dev.vars` is parsed by bundled dotenv 16.3.1 | `dev-vars.ts` (self-check) and `scripts/deployment/test/deployment-dev-vars.test.ts` (parser copy) | `dev` refuses to write the secrets file |
| A `build` block without `cwd` runs its command in the process's working directory (`runCustomBuild`/`runCommand` pass `build.cwd` to the spawn unchanged; the config's `build.cwd` has no default) | `workers/web/wrangler.example.jsonc` (comment on `build`); `scripts/deployment/` runs wrangler from the repository root | `pnpm run web:build` runs in the wrong directory and the deploy fails or ships a stale `workers/web/dist` |

To upgrade:

1. On a branch, set the exact new version in `package.json`, run `pnpm install`, and regenerate types with `pnpm run types`.
2. Run `pnpm test` and both `tsc` commands.
3. For each row in the table, find the cited code in the new `cli.js` and confirm the behaviour is unchanged. Update the line numbers in the comments, and the parser copy in the dev-vars test if dotenv changed. Have a reviewer who didn't do the upgrade (Fable) repeat this check.
4. In the main checkout, run `pnpm run check <name>` and `pnpm run dry-run <name>` for every deployment. `check` doesn't depend on the wrangler version except through `auth token`, so it mainly proves the token step still works.
5. Merge, then deploy as usual. The first deploy after the upgrade shows an empty config diff if the rendered config is unchanged.

## Upgrading the OAuth library

The web client's BFF (`workers/web/src/bff/`) talks to `@cloudflare/workers-oauth-provider` over HTTP and relies on how it answers; each behaviour is cited in a comment by its line in `node_modules/@cloudflare/workers-oauth-provider/dist/oauth-provider.js` (search `workers/web/src/bff` for `oauth-provider.js`), and `workers/web/src/bff/test-server.ts` copies it, so the BFF tests stay green when the library changes. On a library upgrade, re-check each cited line and update the copy. The one most likely to break silently is the stored-client check in `auth.ts` `clientIsKnown`: it revokes a random, malformed token and depends on the library answering `401 invalid_client` for an unknown client or wrong secret *before* it looks at the token, and `200` for a token that isn't three `:`-parts. If either changes, a browser whose registration expired can no longer sign in, or every sign-in registers a new client.

## Leak guard

The repository is public. Don't put real hostnames, account or KV IDs, business or client names, real list or task names, or figures from the owner's account in files or commit messages: use `example.com` hosts, made-up names and made-up numbers, and keep the real values in gitignored files (`deployments/`, `config-live/`).

`pnpm run leak-guard` checks the tree at `HEAD` (`pnpm run leak-guard --log A..B` adds those commits' messages) against private terms kept outside the repository, because a committed list would publish them. Locally the terms are in `.git/leak-patterns`, which every worktree shares. A clone's `pre-push` hook runs `node scripts/leak-guard.ts --pre-push`. CI reads the same list from the `LEAK_PATTERNS` Actions secret and prints only file, line and pattern number. After editing the file, update the secret: `gh secret set LEAK_PATTERNS < .git/leak-patterns`. Rewording a match is the fix. Adding a term is right when something new and private appears.

## Worktrees and local types

Do feature work in a git worktree next to the main checkout, and run `pnpm install --frozen-lockfile` in it: each worktree has its own `node_modules`. Don't symlink the main checkout's copy: pnpm checks `node_modules` against the lockfile before every `pnpm run` and `pnpm exec`, and through a symlink it can try to remove the main checkout's. Deploy from the main checkout: `deployments/` and each `last-deployed.json` are gitignored and per checkout, so a worktree has none. After pulling a change to `pnpm-lock.yaml` into the main checkout, run `pnpm install --frozen-lockfile` before deploying; `pnpm run` refuses until you do (`verifyDepsBeforeRun` in `pnpm-workspace.yaml`).

Generate `worker-configuration.d.ts` (gitignored) from the example config, as CI does: `pnpm run types` (it reads `workers/server/wrangler.example.jsonc` and writes `workers/server/worker-configuration.d.ts`). A copy generated from a local config, or carried over from an older checkout, can disagree with CI's. For example, a required binding the local file lacks lets a cast pass `tsc` locally and fail it in CI.

## Test-driven development

Work test-first. For a feature or a bug fix:

1. Write the test that states the behaviour, run it, and watch it fail for the reason you
   expect. A test that passes before the code exists proves nothing.
2. Write the least code that makes it pass, then run the whole suite (`pnpm test`).
3. Refactor with the suite green.

A bug fix starts with a test that reproduces the bug. Behaviour shared by both hosts goes in
a `workers/server/test/_*-checks.ts` file that `workers/server/test/` (workers) and `workers/server/test-node/` (node) both run.

`workers/server/test-node/api-contract.test.ts` holds the code to `docs/SYNC-API.md`, the contract the app
builds against: every feed field, mutation op, updatable field and capability must be
documented there. When that test fails, update the doc in the same change, or fix the code
if the doc is right.

## Architecture

### Request flow
`workers/server/src/hosts/cloudflare/worker.ts` is the only Worker export (wrangler `main`). It handles `/health` inline, then tries `handleUpload()` → `handleDownload()` → `handleWebhook(req, env, ctx)` (each returns `null` for non-matching paths; `handleWebhook` takes `ctx` because it defers post-202 work to `ctx.waitUntil`), then hands everything else to the OAuth front, `oauthFront()` in `workers/server/src/hosts/shared/oauth.ts` (shared with the Node host), built **per request** by `buildOAuthFront(origin)` in `workers/server/src/hosts/cloudflare/oauth.ts` because the resources differ per deployed hostname and must match what existing grants carry. The front uses the library's (`@cloudflare/workers-oauth-provider` 1.x) role-based form: one `OAuthAuthorizationServer` (issuer `<origin>`; `/authorize`, `/token`, `/register`; resources `<origin>/mcp` and `<origin>/api/v1`, with `defaultResource` and `legacyGrantResource` both `/mcp` so MCP clients that omit `resource`, and pre-1.0 unbound grants, stay on /mcp) and one `OAuthResourceServer` per resource validating locally. Each token is bound to one resource, so an `/mcp` token is refused on `/api/v1` and vice versa (`test*/grant-survival.test.ts` proves grants issued by the old combined `OAuthProvider` keep working). The front routes `/authorize` + `/auth/microsoft/callback` to our auth flow (with `authorizationServer.getOAuthApi(env)` as `env.OAUTH_PROVIDER`), `/mcp` through the grant gate into the `MSToDoSession` Durable Object, `/api/v1` into the client sync API router (`packages/core/api/router.ts`: `/sync/changes`, `/sync/info`, `/tasks/{sid}`, `/search`, and `POST /sync/mutations` in `packages/core/api/mutations.ts`, which runs `applyBatch` (`packages/core/sync/mutations.ts`) through the ops executor (`packages/core/sync/executor.ts`) under one write lease and the host's `waitUntil`; an unauthenticated `GET /api/v1/sync/info` returns only `server_id`), and the rest (metadata, token, registration) to the authorization server. `worker.ts` also exports the cron handler and both DO classes.

### Two Durable Objects (the key topology)
- **`MSToDoSession`** (binding `MCP_SESSION`, **per-session**; class `MSToDoMCP` on binding `TODO_INDEX` before migration v3 deleted the old class's objects) — extends `McpAgent`. Holds the WebSocket session and dispatches tool calls. Registers all tools in `init()`. Deletes itself after a day without a request (`packages/core/mcp/session-expiry.ts`), because Claude never ends its sessions. Owns no task state; it reads tokens from `TODO_CACHE` KV and delegates all refresh to the singleton.
- **`TodoIndex`** (binding `TODO_INDEX_DO`, **singleton** `idFromName("owner")`) — extends `DurableObject`. Owns the SQLite cache (tasks/lists/sync_state), delta-sync orchestration, and is the **sole** caller of the Microsoft token endpoint. A `#refreshChain` promise serializer funnels every refresh through one chain so concurrent sessions don't create refresh storms; an `#identityGeneration` counter invalidates in-flight refreshes when the user re-authorizes as a different account.

> The wrangler binding for the MCP agent is named `MCP_SESSION`, overriding the SDK's default `MCP_OBJECT`. Without this override the SDK throws `env.MCP_OBJECT is undefined`.

### Node host — `workers/server/src/hosts/node/`
One process, one SQLite file (`MSTODO_DB`). `main.ts` is the entry point (bundled by `workers/server/scripts/build-node.mjs` to `dist/main.mjs`; the OAuth library is bundled with `cloudflare:workers` aliased to `cloudflare-workers-shim.ts`). Adapters implement core's ports: `sqlite-db.ts` (`SqlDb`, WAL + `synchronous=NORMAL`), `sqlite-kv.ts` (one `kv` table for `TODO_CACHE` and `OAUTH_KV`, plus the Workers KV spellings the OAuth library calls; `sweepKv()` deletes expired rows at startup and every heartbeat), `state-store.ts` (DO storage + a persisted alarm). `env.ts` `buildNodeEnv()` constructs `IndexCore` **in process** and exposes it through `indexBackend()`, an async proxy with the same surface as the DO stub (every method returns a Promise; `alarm`/`bootstrap` are not reachable). `http.ts` `createHandler()` rewrites every request to `SERVICE_BASE_URL` (**required**, an https origin or loopback http; the Host header is never trusted), caps request bodies (`body-limit.ts`) and refuses a token-less `POST /upload` before reading it, then routes like the Worker into the shared OAuth front; MCP is **stateless** Streamable HTTP (a fresh `McpServer` + transport per POST, JSON responses, GET/DELETE 405). `startScheduler()` replaces the DO alarm and cron: a timer follows the persisted alarm, a failed `alarm()` retries 60 s later, and a 15-minute heartbeat calls `ensureSyncing()`. `single-instance.ts` holds a lease row (heartbeat 20 s, TTL 60 s) so a second process on the same file refuses to start; `lifecycle.ts` releases it on exit, logs (and survives) unhandled rejections, and exits on uncaught exceptions. `HOST` defaults to `127.0.0.1`; `umask 077` keeps the DB files `0600`. Docker: `workers/server/src/hosts/node/Dockerfile` + `compose.yaml` (the build context is the repository root, so the image sees `packages/core`); operator guide: `docs/NODE-HOSTING.md`.

### MCP tool layer — `packages/core/mcp/register-tools.ts`
Both hosts build the server with `createMcpServer()` (`packages/core/mcp/server.ts`), which sets the SDK's `maxToolInputElements` limit. All tools live here and are wrapped by `withGraph(name, fn)`: auth preflight → `GraphError`→named-reason mapping (`list_not_found`, `task_not_found`, `rate_limit_exceeded`, …) → `instrument()`. My Day tools additionally use `withSubstrate()`, which gates on `ENABLE_MY_DAY` and builds a `SubstrateClient`. Handlers return the MCP text envelope (`errResponse()` for failures); `instrument()` logs each call and catches unexpected throws as `unexpected_error` (no unhandled rejections escape the tool layer).

### Write ops — `packages/core/ops/`
The write tools are thin: resolve the list (alias/name → Graph ID), call an op, format the result. The logic lives in plain functions — `tasks.ts` (create/update/delete/move/reorder), `lists.ts`, `steps.ts` (checklist items, incl. reorder), `links.ts` (linked resources), `my-day.ts` (add/remove/reorder) — over an `OpsContext` (`context.ts`: `GraphClient`, on-demand `SubstrateClient`, the index, env, an access-token getter, the write lease). Ops take Graph IDs, return `ToolResult<T>` (`result.ts`: `ok()`/`err(reason, fields)` — the reasons the tools report), and let `GraphError`/`SubstrateError`/`ReauthRequiredError`/`WriteBusyError` propagate for the surface to map. The sync mutations endpoint and the n8n routes are meant to call the same functions (docs/SYNC-API.md §5.5); don't put write logic back in a tool handler. `workers/server/test-node/write-tools.test.ts` snapshots every write tool's output and call sequence end to end. **Single write queue:** every op runs inside `ctx.writes.run()` (`write-lease.ts`), a lease held by `IndexCore` (`acquireWriteLease(holder, ttlMs, waitMs)`/`releaseWriteLease`) because the writes run in the caller and closures can't cross DO RPC. Waiters queue FIFO inside the index (up to 50 s for MCP, then `write_busy`); the 10 s lease is renewed every ~3 s and persisted in the StateStore; only a failed *first* acquire proceeds unserialized (logged). One `WriteLease` is one writer (its `run()` calls serialize); hold the lease across several ops with `hold()`. Steps after the Graph/Substrate write commits (index write-throughs, link rules) must never fail the op.

### Two Graph clients (intentional)
- `packages/core/graph/client.ts` (`GraphClient`) — `graph.microsoft.com/v1.0`, token audience `graph.microsoft.com`. Standard CRUD + delta + sub-resources.
- `packages/core/graph/substrate-client.ts` (`SubstrateClient`) — `substrate.office.com` (Exchange Online audience), the undocumented endpoint the To Do web app uses. Required because **Graph's `todoTask` has no `CommittedDay` field — My Day is invisible to Graph**. Substrate uses PascalCase Outlook shapes. Also powers **lossless cross-list move** via `reparentTask()` (PATCH `ParentFolderId`), which preserves checklist items / attachments / linked resources / My Day that a Graph create+delete would lose. See `packages/core/ops/move-task.ts` for the three-stage safety net (reparent → confirm `ParentFolderId` → only fall back to copy/delete if the source is confirmed still present). Also powers **checklist-item (subtask / "step") manual ordering** — Graph's `checklistItem` has no order field, so order is Substrate-only via `OrderDateTime` (same descending semantics as a task's). Read–write asymmetry, both verified live: the steps are **read INLINE** as a `Subtasks[]` array on the folder-scoped task GET (`listSubtasks(folderId, taskId)` does `GET /taskfolders/{folder}/tasks/{id}?$select=*` — there is **no** standalone subtasks collection; `GET /tasks/{id}/subtasks` 400s "Endpoint not supported"), but the **write is folder-free** per-item (`patchSubtask(taskId, subtaskId)` → `PATCH /tasks/{id}/subtasks/{subtaskId}`). A step's `OrderDateTime` is **null until it is first dragged** — un-reordered steps have no stored order and display in `createdDateTime` order. This is why **checklist order is never cached** (see the checklist-cache section): caching would mostly store nulls and add a per-scan Substrate call, while Graph's `createdDateTime` is the free, correct fallback. Backs the `reorder_checklist_item` tool and the live-order enrichment on `list_checklist_items` + `get_task` `include_checklist_order`.

Both clients: **host-pin** before attaching the Bearer token (prevents token leak via a malicious `@odata.nextLink`), retry once on 401 after a forced refresh, and handle 429 (Graph: 1 retry; Substrate: 2, EXO throttles harder). Neither holds tokens — they take a `TokenProvider` interface.

### Delta sync & SQLite — `packages/core/index/index-core.ts` (hosted by `workers/server/src/hosts/cloudflare/todo-index-do.ts`), `packages/core/index/sql.ts`, `packages/core/graph/delta.ts`
`TodoIndex.runSyncCycle()` syncs the list roster (`$delta` on `/me/todo/lists`) then per-list tasks (incomplete lists first, capped `MAX_PAGES_PER_CYCLE=30`/cycle). `delta.ts` `followToTerminal()` walks `@odata.nextLink` chains into a `DeltaRow[]` union (`removed` | `task`) until `@odata.deltaLink`; a 410 (expired token) triggers a re-baseline. The `alarm()` re-arms itself (2s mid-sync, else `DELTA_SYNC_INTERVAL_MIN`); the `*/15` cron calls `ensureSyncing()` as a heartbeat to re-arm after DO eviction. SQLite tables: `tasks` (Graph `dateTimeTimeZone` flattened to epoch ms), `tasks_fts` (FTS5 external-content mirror kept current by triggers — powers `search_tasks`), `lists`, `sync_state`.

### Auth & the OWNER_EMAIL gate — `workers/server/src/hosts/shared/auth-handler.ts`, `packages/core/auth/microsoft.ts`
`/authorize` shows a per-client **consent page** (`workers/server/src/hosts/shared/consent-page.ts`) before any redirect to Microsoft — the confused-deputy mitigation for open DCR. It uses the library's `beginConsent`/`approveConsent`/`beginUpstream`/`finishUpstream` helpers (browser-bound `__Host-` cookies; the Microsoft `state` exists only after approval); remembered consent is signed with a key HKDF-derived from `MS_CLIENT_SECRET` (`packages/core/auth/crypto.ts`, which also seals the KV tokens with AES-GCM). Every grant's props carry `{user, epoch, authorized_at}`; `grantRefusal()` (`packages/core/auth/grant.ts`) checks them against `TodoIndex.authState()` on **every `/mcp` and `/api/v1` request** (the resource servers' handlers in `workers/server/src/hosts/shared/oauth.ts` and `handleApiRequest` in `packages/core/api/router.ts`, using that request's `ctx.props` — `McpAgent`'s `this.props` is the session's *first* token and is never refreshed, so it must not be used for authorization) and **every refresh** (`tokenExchangeCallback`). The `#tool()` preflight adds the caller-independent checks (Microsoft re-auth pending, tokens present). The epoch and the Microsoft re-auth flag live in DO storage, not KV, so revocation is immediate. PKCE S256 against Entra. Scopes are `Tasks.ReadWrite offline_access User.Read`, plus `https://outlook.office.com/Tasks.ReadWrite` when `ENABLE_MY_DAY=true` (two audiences, one refresh token → both a Graph and a Substrate token). On callback, `isOwner()` checks `/me.userPrincipalName` against the `OWNER_EMAIL` secret and **403s non-matching users before any token is stored**. A match on `/me.mail` alone counts only when `OWNER_OBJECT_ID` is set and equals `/me.id` (`mail` is admin-settable; a UPN must be on a verified domain). `OWNER_OBJECT_ID`, when set, must always match, and it's required (fail-closed) when `MS_TENANT_ID` is `common`/`organizations`. A changed `/me.id` triggers `wipeIdentityScopedState()` in fail-closed order (DO reset → KV token wipe → identity delete → alias clear). The `AADSTS65001` latch (`#substrateUnavailable`) returns `my_day_unavailable` without re-minting once the EXO scope is found unconsented.

### Web client — `workers/web/`
A web app on its own Worker that reads and edits tasks (`workers/web/wrangler.example.jsonc`, deployed as `kind: "web"`, see Deployments). `src/hosts/cloudflare/worker.ts` is the only Worker export and the only file that knows bindings; it checks `SERVER_ORIGIN`, `WEB_ORIGIN`, `WEB_SESSION_SECRET` and the session limits on every request (a bad one answers 503 naming the variable), refuses a hostname other than `WEB_ORIGIN` (421), hands `/auth/*` and `/bff/*` to the backend-for-frontend, and serves everything else from `ASSETS` (`run_worker_first`, SPA fallback). The BFF (`src/bff/`, host-independent) is an OAuth client of the server's `/api/v1` resource: each browser registers its own client (dynamic registration, "Potem Web", device cookie), so two browsers hold two grants. Tokens live only in the AES-GCM-sealed `__Host-` session cookie (key HKDF-derived from `WEB_SESSION_SECRET`, one `info` per cookie; one that fails to unseal counts as absent); page JavaScript never sees them. `/bff/api/*` is a proxy over an allowlist of sync API paths: `GET` for `sync/info`, `sync/changes`, `search`, `tasks/{id}`, `attachments/{id}`, `theme-images/{id}`, `link-rules` and `lists/excluded`, and the one write, `POST sync/mutations` (CSRF headers, `Content-Type: application/json`, a body of at most 256 KiB, the exact bytes forwarded); any other method on an allowlisted path is 405, `Set-Cookie` is never forwarded, and it never refreshes the token itself: near expiry it answers `401 session_refresh_needed` and the page sends one `POST /bff/session/refresh` (only `GET /bff/session` and the refresh write the cookie, so concurrent requests can't put back a superseded refresh token). State-changing routes need `X-Potem: 1` and an `Origin` equal to `WEB_ORIGIN`. `src/bff/headers.ts` adds the CSP (`script-src 'self'`, `form-action` limited to the server origin), `nosniff`, `no-referrer`, `noindex` and `Strict-Transport-Security: max-age=31536000` to every response (HSTS without `includeSubDomains` or `preload`: the web hostname shares a zone with other hosts, so it covers that host only), and `no-store` and `Cross-Origin-Resource-Policy: same-origin` to `/auth/*` and `/bff/*`; `/bff/api/*` gets a sandboxing CSP with `frame-ancestors 'none'`. The app (`src/app/`, React) pulls the change feed into the sync engine's in-memory mirror (`src/sync/`); nothing is persisted yet, so a reload re-pulls. Edits go through the outbox (`src/sync/outbox.ts`): each mutation gets its id once and keeps it across retries (a retry the server already applied answers `duplicate`); a batch holds at most 25 mutations and 192 KiB; one request is in flight; a batch the server refuses permanently (HTTP 400, 403, 413 or 415) is bisected until the one refused mutation leaves as rejected; transient failures retry with a 1 s to 30 s backoff, and a mutation still answered `failed` with retry after 6 answers or 5 minutes leaves as rejected; a `duplicate` is read as the result the server stored. After each answered batch the outbox pulls with `loader.pullAfter()`, which starts after any pull already in flight (that one may predate the server's write); an applied edit stays in the overlay until such a pull succeeds, and a failed pull is retried from 2 s. The overlay (`overlay.ts`): `store.task()` and `store.tasks()` show pending edits over the mirror, `baseTask()` and `baseTasks()` show the server's state, and the outbox feeds the store through `setPending`. Pending edits survive a 410 resync and are dropped on sign-out, which discards unsent edits (the sign-out screen counts them); the Sign out button first gives the outbox up to 3 s to send them. A task's HTML note is read-only in the web client, so a flagged email's formatting is never flattened; the rest of that task can still be edited. `src/app/edits.ts` and `editing.ts` turn UI actions into mutations. Task bodies render as plain text from the engine's `bodyText`, never as HTML, and link `href`s outside `http:`, `https:` and `mailto:` are dropped. Boundaries, each enforced by a test: the engine imports only core types (`src/sync/boundary.test.ts`); the BFF imports no React, no `cloudflare:*`, nothing from `src/hosts` or `src/app`, and uses no browser globals (`src/bff/boundary.test.ts`). `workers/web/spike/` is the earlier synthetic-feed demo (`pnpm run web:spike`).

### Config — `packages/core/config/`
Three Zod-validated blobs (`schemas.ts`) read/written to fixed `TODO_CACHE` KV keys (`config:lists`, `config:link_rules`, `config:attachments`) via `loader.ts`, **no in-memory cache** (fresh KV read per tool call). `ListsConfig` drives `classifier.ts` (regex list classification after `stripEmoji()`), `query-scope.ts` (multi-list filtering + `completed`→Graph status enum), and `aliases.ts` (alias→name→id resolution). `link-rules-engine.ts` `runLinkRules()` is pure with DoS guards (8 KB body cap, 50 ms budget); To Do allows exactly one linked resource per task so it stops at first match.

### Observability — `packages/core/log.ts`, `packages/core/observability/instrument.ts`
`log.{debug,info,warn,error}(event, fields)` emits structured JSON (Workers Observability is enabled in `workers/server/wrangler.example.jsonc`). `instrument()` emits a `tool` event with `{name, durationMs, ok, reason}`. Both Graph clients redact query strings before logging (delta tokens / `$filter` carry sensitive data).

### Bindings (see `workers/server/wrangler.example.jsonc`, types in `workers/server/src/hosts/cloudflare/types.ts` and `packages/core/ports.ts`)
- KV: `OAUTH_KV` (PKCE/OAuth state, upload/download capability tokens), `TODO_CACHE` (tokens, the three config blobs)
- DO: `MCP_SESSION` (`MSToDoSession`), `TODO_INDEX_DO` (`TodoIndex`)
- R2 (optional): `BLOBS` — the blob store (`packages/core/blobs.ts`, docs/SYNC-API.md 4.9). Attachment copies under `attachments/<sid>`, app theme images under `theme-images/<id>` (id = first 32 hex of the bytes' SHA-256, also its sid). The app's download route and the connector (`packages/core/attachment-cache.ts`: `get_attachment`, `/download`, upload links) read and fill the same copies. Without it, downloads stream from Graph and the theme-image routes answer 501. The cron sweeps it daily at 08:00 UTC. App-owned appearance (theme images, a list's `image_id`/`image_style`, smart-list themes in the `app_settings` entity) lives only in the index (migration v13), never in To Do.
- Secrets: `MS_TENANT_ID`, `MS_CLIENT_ID`, `MS_CLIENT_SECRET`, `OWNER_EMAIL`, optional `OWNER_OBJECT_ID`
- Vars: `TIMEZONE`, `DELTA_SYNC_INTERVAL_MIN`, `LIST_METADATA_SOFT_TTL_SEC`, `SERVICE_BASE_URL`, `ENABLE_MY_DAY`, `ENABLE_DOWNLOAD_LINKS`, `ENABLE_TASK_SUBSCRIPTIONS`, `MAX_SUBSCRIPTION_OPS_PER_CYCLE`, `MY_DAY_SCAN_EVERY_N_CYCLES`, `MY_DAY_SCAN_MAX_FOLDERS_PER_CYCLE`, `ENABLE_CHECKLIST_CACHE`, `CHECKLIST_SCAN_MAX_TASKS_PER_CYCLE`
- Optional, off when unset: `ACCESS_TEAM_DOMAIN` + `ACCESS_AUD` (+ `ACCESS_HANDOFF_REDIRECT_URIS`, the only redirect URIs that receive the Access token) (Cloudflare Access verified in the server on every `/api/v1` path and `/app/signin`; `packages/core/auth/access.ts`, `workers/server/src/hosts/shared/app-signin.ts`; one without the other fails closed with 503), `APPLE_TEAM_ID` + `APPLE_BUNDLE_IDS` (`/.well-known/apple-app-site-association`). The Access gate sits in `oauthFront` before every `/api/v1` route, so new routes are covered without registering anything.

`create_upload_link` mints an unguessable capability token into `OAUTH_KV` (`upload:` prefix); the `/upload` handler (`packages/core/upload/`) burns it on first use, giving the browser an upload surface without the OAuth token.

`mint_download_link` is the inverse (ROADMAP §9): the same capability machinery (`packages/core/upload/tokens.ts`, distinct `download:` prefix, ≤5-min TTL) scoped to one attachment, served by the public `/download` handler (`packages/core/upload/download-handler.ts`, wired in `worker.ts` right after `handleUpload`). The handler burns the token **before** the Graph fetch (single-use on first reachable GET, not transactional) and reuses `getAttachmentBytes()` to move bytes server-to-server without the model in the loop. Gated by the `ENABLE_DOWNLOAD_LINKS` var (defaults on; `"false"` disables both the tool and the endpoint).

### Graph change-notification subscriptions — `packages/core/subscriptions/` (ROADMAP §4)
Gated by `ENABLE_TASK_SUBSCRIPTIONS` (default ON; `"false"` disables the public webhook + all subscription creation). Three modules: `gate.ts` (`taskSubscriptionsEnabled`, `webhookUrl`, lifetime/renew/budget constants), `manager.ts` (pure Graph create/renew/delete/list over an injected `GraphClient` — host-pinned, sole-refresher invariant intact), and `webhook-handler.ts` (`handleWebhook`). The `subscriptions` SQLite table (migration **v2**: `subscription_id`/`list_id`/`client_state`/`expiration_ms`) lives in `TodoIndex`, which owns reconcile (`reconcileSubscriptions`, diff roster↔records) + renew (`renewSubscriptions`) — both **budgeted** by `MAX_SUBSCRIPTION_OPS_PER_CYCLE` and called from `runSyncCycle`'s calm-cycle block. `handleWebhook` echoes Graph's `?validationToken` synchronously (DO-free) and acks real notifications `202` within Graph's 3s window, deferring `TodoIndex.onChangeNotification()` to `ctx.waitUntil`. **Invariant — the notification path is read-only toward Microsoft task data:** `onChangeNotification` validates `clientState`, arms the alarm (Graph delta refreshes Graph fields), and does a *targeted* single-task Substrate `getTask` to refresh that task's My Day fields (mark-scan-due fallback for a not-yet-cached task). It issues **zero** mutating Graph/Substrate calls, so it can never emit a `todoTask` notification → no feedback loop. **Delta polling stays mandatory** (no missed-notification safety net for `todoTask`); subscriptions only change *when* a cycle runs.

### Checklist-item cache — `packages/core/checklist/gate.ts` + `TodoIndex`
Gated by `ENABLE_CHECKLIST_CACHE` (**default OFF** — opt-in; it adds a one-time per-task backfill). Makes checklist items queryable **across tasks** (Graph has no `hasChecklist` boolean and `$delta` carries no expansions, so checklist contents are never free — they're fetched per task). Same architecture as the My Day cache: migration **v3** adds a queryable `checklist_items` table + a `checklist_fts` FTS5 mirror (three triggers, `AFTER UPDATE OF display_name` so a check/uncheck toggle doesn't churn the index) + a `tasks.checklist_synced_at` marker column (excluded from `TASK_COLUMNS`, like the Substrate `committed_*` columns, so the delta UPSERT never clobbers it). The marker unifies backfill + incremental: `NULL` means "fetch this task's checklist." `#applyRows` nulls it whenever a task rides `$delta` (checklist edits bump `lastModifiedDateTime` → ride delta — **verified live**), and a **budgeted** per-task scan (`#runChecklistScanBatch`, `CHECKLIST_SCAN_MAX_TASKS_PER_CYCLE`, **open tasks only**, newest-changed first, `shouldSkipSync` set) drains the NULL set on calm cycles via `listChecklistItems` (`packages/core/graph/todo-resources.ts`) → `replaceChecklistItems`. **Independent of `ENABLE_TASK_SUBSCRIPTIONS`** — the change signal is delta (always on the timer); subscriptions only lower latency. Scan errors are **non-destructive** (leave the marker NULL, never mutate the task row), so an unreachable checklist can't corrupt cached task state; a 404'd task is reconciled by the next delta removal. **Intentional scope:** the cache covers **open tasks in non-skipped lists only** — **completed tasks are deliberately excluded** from the cross-task checklist cache (follow-ups are an open-task concern; `get_task` still returns any single task's items live), and skipped lists (`shouldSkipSync`) are never cached. There is **no** lazy-fill for completed tasks; this is by design, not a gap. The three `*_checklist_item` MCP tools write through (`upsertChecklistItem`/`deleteChecklistItem`, gated) for instant visibility; `deleteTask` cascades to `checklist_items`. New capability: `query_tasks` `has_open_checklist_item` filter; the `search_checklist_items` tool (`searchChecklistItems`: FTS over item text, or — no query — pending items oldest-first, grouped by task); and `search_tasks` `include_checklist` (default ON) which widens task FTS to checklist text via a **tiered** `search()` (title/body matches first by BM25 rank, then checklist-only matches appended — the two FTS corpora have incomparable rank scales, so they're tiered not merged). Naming stays `checklist` (matches the API + the existing tools); descriptions carry the `subtask`/`step` synonyms so the model connects the UI's "Steps" and the user's "subtask" to these tools. **Item ORDER is deliberately NOT part of this cache** — it's Substrate-only (`OrderDateTime`), null until a step is first dragged, so caching it would mostly store nulls + add a per-scan Substrate call while Graph's `createdDateTime` is the free correct fallback. Order is instead read **live on demand**: `list_checklist_items` enriches it best-effort (one Substrate `listSubtasks` round-trip when My Day/EXO is on; sorts by `OrderDateTime` desc, nulls last; adds `ordered` + per-item `orderDateTime`; falls back to Graph creation order otherwise), `get_task` does so opt-in via `include_checklist_order`, and `reorder_checklist_item` writes it. See the Substrate-client section for the read-inline / write-folder-free asymmetry.

## Secrets in `deployments/<name>/.dev.vars`
`pnpm run secrets <name>` pushes `MS_TENANT_ID`, `MS_CLIENT_ID`, `MS_CLIENT_SECRET`, `OWNER_EMAIL` and `OWNER_OBJECT_ID` to Cloudflare over stdin (never argv); `pnpm run dev <name>` resolves the same file into a temporary `.dev.vars` that it deletes on exit. A value may be a literal **or** a 1Password reference `op://<vault>/<item>[/<section>]/<field>`, resolved via the `op` CLI (needs `op signin` or `OP_SERVICE_ACCOUNT_TOKEN`; `op_account` in `deployment.jsonc` picks the account); surrounding quotes are stripped, so 1Password's "Copy Secret Reference" pastes in verbatim.

## Release process

Releases are cut **from `dev`**, then merged/pushed to `main` and tagged. The convention (see prior `Release X.Y.Z: …` commits):

1. Confirm what's pending: `git log --oneline main..dev` (and `git fetch origin dev && git log --oneline dev..origin/dev` — if local `dev` is behind, rebase your work onto `origin/dev` first so the push stays a fast-forward).
2. In `CHANGELOG.md`, rename the `## [Unreleased]` heading to `## [X.Y.Z] – YYYY-MM-DD` (en dash `–`, Keep-a-Changelog format, sections ordered Added/Changed/Fixed/…), add any missing entries, and open a fresh empty `## [Unreleased]` above it.
3. Bump `version` in **`package.json`** (`pnpm-lock.yaml` records no version of its own).
4. Commit as `Release X.Y.Z: <theme>`.
5. **Tag — signed/annotated, never lightweight.** The repo sets `tag.gpgsign=true` with `gpg.format=ssh`, so use `git tag -s vX.Y.Z -m "Release X.Y.Z: <theme>"` (a bare `git tag vX.Y.Z` makes a *lightweight, unsigned* tag — wrong, and prior tags are signed `tag` objects). Verify with `git tag -v vX.Y.Z` (expect `Good "git" signature`). **Tags are protection-ruled on GitHub: the remote ref cannot be force-overwritten or deleted**, so get the signed tag right *before* pushing it — a pushed lightweight tag can't be cleanly upgraded in place.
6. Push `dev` and the tag: `git push origin dev && git push origin vX.Y.Z`.
7. **Merge to `main` via PR, not a local fast-forward.** `main` carries the `Merge pull request #N from dszp/dev` merge commits from every prior release, so it has diverged from `dev` and a local `git merge --ff-only` is impossible by design. Use `gh pr create --base main --head dev --title "Release X.Y.Z: …" --body …` then `gh pr merge <#> --merge` (a merge commit, matching #9–#12). The signed `vX.Y.Z` tag stays on the `Release` commit (now in `main`'s history); don't re-tag the merge commit.
8. Deploy each deployment (`pnpm run deploy <name>`, from the main checkout) and confirm its `/health` if this release ships code (often already deployed from `dev` before cutting the release — check first).

## Conventions & invariants worth preserving
- **Only `IndexCore` refreshes tokens** (hosted by the `TodoIndex` DO on Cloudflare, in process on Node). Don't add token-endpoint calls elsewhere; route through its serializer.
- **Core import boundary.** `packages/core/**` (imported elsewhere as `@potem/core/<path>`, a `paths` alias in `tsconfig.json` and a vitest alias) never imports `cloudflare:*`, `agents`, `@cloudflare/*`, or anything under `workers/server/src/hosts/` (enforced by `workers/server/test/core-boundary.test.ts`). `workers/server/src/hosts/node` never imports `workers/server/src/hosts/cloudflare`, and `workers/server/src/hosts/shared` imports neither host (`workers/server/test-node/host-boundary.test.ts`).
- **Web sync engine boundary.** `workers/web/src/sync` imports no React, no server code and nothing outside its directory except `@potem/core` types (`import type`, enforced by `workers/web/src/sync/boundary.test.ts`), and uses no DOM, Node or Workers globals (`workers/web/tsconfig.engine.json`). A rule it shares with core, such as a body's plain text, is a copy held to core's by shared test cases.
- **No host switches in core.** A behavior that differs by host is a port in `packages/core/ports.ts`, implemented by each host — never `if (isCloudflare)`.
- **Each host bounds request bodies.** Core's upload handler buffers a body it cannot size in advance; Cloudflare's platform caps bodies, the Node host caps them in `createHandler`. A new host must do the same.
- **Host-pin before attaching a Bearer token** — keep `assertGraphUrl` / `assertSubstrateUrl` in front of every authed request when adding endpoints.
- **The server is strictly single-user.** The `OWNER_EMAIL` 403 gate and identity-change wipe are load-bearing; don't loosen them.
- Register tools with `#tool()` — it applies the auth preflight (Microsoft re-auth pending, tokens present) to every tool, including cache-only ones; the grant epoch/age check runs per request in `workers/server/src/hosts/shared/oauth.ts` (both hosts). Graph tools also go through `withGraph` (and `withSubstrate` for My Day) for error mapping (`reauth_required` included) and instrumentation.
- **A refused Microsoft refresh is classified, not just thrown.** `reauthReasonFromTokenError` marks re-auth only for `invalid_grant` / `interaction_required` / `consent_required` on the **Graph** refresh; the same codes on the Exchange (Substrate) mint only latch My Day off. Transient failures must never lock the owner out. A CAE claims challenge on a 401 is reported via `reportClaimsChallenge`, not retried.
- **Naive date strings are local time** (`TIMEZONE`), via `packages/core/util/dates.ts` — never pass a model-supplied date to Graph labelled UTC.
- Graph silently ignores `$expand=attachments`; fetch `/attachments` as a sub-resource collection (`packages/core/graph/todo-resources.ts`).
